# TechHub 多租户 SaaS 产品需求文档（PRD）

> 版本：v1.0 ｜ 日期：2026-09-07 ｜ 状态：已实现（2026-09-08）  
> 关联文档：[技术方案](MULTI-TENANT-TECH.md)

---

## 1. 背景与目标

### 1.1 现状

TechHub 当前为**单学校**部署形态：`schools` 表虽已存在，但系统实际只服务一所学校，所有班级、教师、学生都挂在一个默认学校下。现有角色仅有 `admin`（系统管理员，全局唯一）、`teacher`（班主任/科任）、`student` 三种。

### 1.2 目标

将 TechHub 改造为**多租户 SaaS 平台**：

- **多学校共用一套系统**：平台可接入多所学校，每所学校是独立租户。
- **严格数据隔离**：任何租户的数据对其他租户完全不可见、不可访问，包括越权场景。
- **每校完整角色体系**：每个学校独立拥有「学校管理员、班主任、教师、学生」四类角色，互不干扰。

### 1.3 成功标准（非功能）

| 指标    | 目标                            |
| ----- | ----------------------------- |
| 数据隔离  | 跨学校数据访问**零泄露**（接口层 + 数据层双重拦截） |
| 租户规模  | 单套部署支撑 100+ 学校、每校 1000+ 学生    |
| 改造兼容性 | 现有单学校数据平滑迁移，历史功能不回归           |

## 2. 术语定义

| 术语                    | 说明                                |
| --------------------- | --------------------------------- |
| 租户（Tenant）            | 一所学校，数据隔离的基本单元，对应 `schools` 表一条记录 |
| 平台超管（super_admin）     | 平台运营方，跨租户管理所有学校，不属于任何学校           |
| 学校管理员（school_admin）   | 每个学校的最高管理员，管理本校班级/教师/学生           |
| 班主任                   | 绑定某班级的教师（`classrooms.teacher_id`） |
| 科任老师                  | 与班级多对多关联的教师（`class_teachers`）     |
| 租户上下文（Tenant Context） | 当前请求所属的学校 ID，贯穿鉴权与查询过滤            |

## 3. 租户与角色模型

### 3.1 角色层级

```
平台超管 super_admin（跨学校，平台级）
   └── 学校管理员 school_admin（每个学校 1 到多个）
          ├── 班主任（head teacher，绑定班级）
          ├── 科任老师（subject teacher，关联班级）
          └── 学生 student（归属班级）
```

### 3.2 角色映射（现有 → 改造后）

| 现有角色      | 改造后                                | 说明                                                    |
| --------- | ---------------------------------- | ----------------------------------------------------- |
| `admin`   | 拆分为 `super_admin` + `school_admin` | 现有 admin 为全局上帝账号，改造后平台超管保留全局能力，学校管理能力下沉到 school_admin |
| `teacher` | 保持 `teacher`                       | 班主任/科任由班级关联关系决定，不新增 role                              |
| `student` | 保持 `student`                       | 归属学校 + 班级                                             |

### 3.3 租户模型

- 租户 = `schools` 表一条记录，新增字段：`status`（active / disabled）、`admin_user_id`（学校管理员，可选快捷入口）等。
- 平台超管的 `school_id = NULL`（表示不属于任何租户）。
- 所有其他账号 `school_id` 必填，指向所属学校。

## 4. 功能需求

### 4.1 学校开通（平台超管）

- 平台超管创建学校（名称、代码、地址、电话），并为学校指定/创建首位学校管理员账号。
- 学校可启用/停用（停用后该校所有账号不可登录）。
- 平台超管可查看所有学校的统计概览（学校数、学生数、活跃度）。

### 4.2 学校管理员工作台（school_admin）

学校管理员登录后，在本校范围内：

- **班级管理**：新建/编辑/毕业班级，指定班主任、配置科任老师。
- **账号管理**：创建/编辑/删除本校教师账号（班主任/科任）、重置密码。
- **学生管理**：批量导入/导出本校学生，编辑学生档案、退学处理。
- **数据看板**：仅统计本校数据。
- **审计日志**：查看本校全部审计日志。

> 学校管理员**不能**跨学校操作，**不能**管理其他学校管理员或平台超管。

### 4.3 教师端（班主任 / 科任老师）

与现有功能一致，但数据范围收敛为「**本校 + 自己负责的班级**」：

- 学生管理、成绩、积分、考勤、沟通、谈心、表现、评语、课表、活动、座位、周报、看板、作业。
- 作业附件（多附件）、出勤率统计、移动端（`/m`）等近期功能全部保留。

### 4.4 学生端

与现有功能一致，但数据范围收敛为「**本校 + 自己班级**」：

- 查看/提交作业、优秀作品、编程练习、个人资料。

### 4.5 登录

- **学生**：选择学校 → 班级 + 姓名 + 密码。
- **教师 / 学校管理员**：选择学校（或记住上次学校）→ 用户名 + 密码。
- **平台超管**：用户名 + 密码（独立入口或同一入口自动识别）。

### 4.6 数据隔离（核心）

- 所有查询、写入、导出、导入、统计，强制带上当前用户的 `school_id` 过滤。
- 跨学校访问（直接拼 ID）返回 403/404，不得泄露任何数据。
- 学生选择器、班级选择器、看板、审计日志等所有下拉与列表，均只出现本校数据。

## 6. 非功能需求

### 6.1 安全

- 数据隔离在**接口层 + 数据层**双重实现，任何一处失效都不导致泄露。
- 登录失败锁定、密码强度、首次改密、审计日志等现有安全机制在多租户下继续生效。
- 审计日志记录 `school_id`，确保跨学校审计不串数据。

### 6.2 性能

- 所有涉及租户的查询走 `school_id` 索引，避免全表扫描。
- 高频表（scores/attendance/submissions）`(school_id, ...)` 组合索引。

### 6.3 可扩展

- 预留「独立数据库 / 独立 schema」升级路径（通过 `school_id` 抽象，未来可按租户分库）。

## 7. 迁移策略（现有单学校 → 多租户）

1. **默认租户**：现有学校数据（1 所学校 + 全部班级/学生/业务数据）迁移为一个默认租户。
2. **角色迁移**：
   - 现有 `admin` → 平台超管（`super_admin`），保留全局管理能力。
   - 现有 `teacher` → 归入默认租户，作为班主任/科任。
   - 现有 `student` → 归入默认租户。
3. **数据回填**：所有业务表回填 `school_id = 默认租户 ID`。
4. **灰度验证**：先在默认租户回归验证，再开放多学校创建。

## 9. 待决问题（已决，随 v1.0 落地）

| 问题 | 决策 |
| ---- | ---- |
| 是否保留「学校自助注册」入口 | 仅平台超管开通学校（`POST /api/schools` 可同步创建首位学校管理员） |
| 学生登录是否「记住学校」 | 记住上次学校（前端 `localStorage`，登录页仍可切换） |
| 教师是否可属于多所学校 | 不支持，教师绑定单一学校（`users.school_id` 必填） |
| 计费/订阅是否本期纳入 | 不纳入，仅预留 `schools.status` 等字段 |
