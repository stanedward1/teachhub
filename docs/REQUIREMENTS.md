# TechHub 移动端 MVP 需求规格（PRD）

> 状态：草稿 v0.1 ｜ 负责人：产品 ｜ 目标用户：班主任、管理员（内部角色）

## 1. 问题陈述

班主任/管理员的日常工作大量发生在「离开电脑」的现场——课堂上、宿舍查寝、操场、家访路上。这些场景需要的是**单手 30 秒内完成一次录入或查询**，而不是回到办公桌前做完整管理。

现有系统基于 Vue3 + Element Plus 桌面组件，虽有移动端 CSS 适配，但密集表格、复杂表单在手机上是「能用但别扭」：教师往往当场先记在脑子里/纸上，回到电脑才补录，造成**记录遗漏、时效差**，进而导致后续的数据看板与「学生画像」失真。

**不解决的代价**：数据质量下降（画像/看板失真）＋ 教师双端割裂的糟糕体验 ＋ 高频功能被桌面端束缚，使用率上不去。

## 2. 目标

**用户目标（Outcomes，非 Outputs）**
- 高频操作（随手记表现、谈心、考勤、请假审批）在手机端 **≤30 秒** 完成
- 随时随地**快速调取**学生画像/成绩/积分，与家长沟通时有据可依
- 不在办公室也能**及时审批请假**

**业务目标**
- 移动端承接 ≥80% 的「高频录入类」操作，降低数据遗漏率
- 教师/管理员日活跃（DAU）随移动端上线提升

**技术目标**
- 复用现有 Vue3 + FastAPI，**不引入第二套技术栈**，控制维护成本

## 3. Non-Goals（本版本明确不做）

| 不做的事 | 原因 |
| ---- | ---- |
| 微信小程序 / 原生 App | 教师无所谓载体，且为内部用户，无需微信生态分发 |
| 学生端 / 家长端 | 本次只覆盖班主任 + 管理员 |
| 全功能移动端（班级/账号管理、Excel 导入导出、审计日志、长文作业编辑） | 重管理功能留在桌面端，避免搬移成本 |
| 完全离线数据写入 | PWA 只做「可安装 + 外壳」，不强求离线编辑 |
| 消息推送（原生 push） | 需后端推送通道，放 P2 规划 |

## 4. 用户故事（按优先级排序）

1. 作为班主任，我希望**在现场用手机随手记录学生表现（积极/消极）**，以便当场记录、不遗漏。
2. 作为班主任，我希望**快速查看某学生的画像、成绩、积分**，以便和家长沟通时有据可依。
3. 作为班主任，我希望**用手机一键完成考勤打卡/点名**，以便节省课堂时间。
4. 作为班主任，我希望**在手机上查看并审批学生请假**，以便不在办公室也能及时处理。
5. 作为班主任，我希望**快速记录与学生谈心内容**，以便记录及时、内容不丢。
6. 作为管理员，我希望**在手机上查看数据看板速览（今日请假、待办）**，以便随时掌握全局。

## 5. 需求（MoSCoW 分级）

### P0 — Must-Have（缺失则功能不成立）

| # | 需求 | 说明 | 验收要点 |
| --- | ---- | ---- | ---- |
| R1 | 移动端登录 | 复用现有 JWT，支持「记住登录」 | 打开即用，Token 有效期内免重复登录 |
| R2 | 学生速查 | 画像速览（五维雷达概览）+ 成绩 + 积分，精简字段 | 3 步内定位到学生，列表可搜索 |
| R3 | 随手记表现 | 选学生 → 选积极/消极 → 记录内容 → 提交（自动联动积分） | 30 秒内完成；表现落库并同步生成积分 |
| R4 | 考勤打卡 | 按班级一键点名，标记出勤/缺勤/请假 | 全班点名 ≤2 分钟 |
| R5 | 请假查看/审批 | 列表查看请假，支持「登记/销假」操作 | 手机上完成审批，状态实时同步 |
| R6 | 谈心速记 | 选学生 → 输入内容 → 提交 | 即时保存，与桌面端谈心记录打通 |

### P1 — Should-Have（显著提升体验，核心链路可不依赖）

| # | 需求 | 说明 |
| --- | ---- | ---- |
| R7 | 数据看板速览 | 今日请假数、待办、我的班级概览 |
| R8 | PWA 可安装 | manifest + service worker，「添加到主屏幕」，二次进入秒开 |
| R9 | 待办提醒 | 待审批请假、未处理事项角标提示 |

### P2 — Could-Have（v1 不做，架构上预留）

- 原生消息推送（依赖后端推送通道 + 各平台限制）
- 离线缓存（弱网可用）
- 学生/家长端扩展

## 6. 成功指标

| 指标 | 类型 | 目标（假设值，待校准） | 衡量方式 |
| ---- | ---- | ---- | ---- |
| 移动端功能使用率 | 领先 | 上线 30 天 ≥60% 教师使用 | 后端埋点/审计日志 |
| 单次录入时长 | 领先 | 表现/谈心 ≤30 秒 | 埋点或可用性测试 |
| 数据遗漏率 | 滞后 | 相对桌面端下降 | 对比移动端上线前后录入量 |
| 教师 DAU | 滞后 | 提升 | 登录日志 |

> 目标值为假设，需以真实使用数据校准。

## 7. 待决问题（Open Questions）

| 问题 | 谁决策 | 是否阻塞 |
| ---- | ---- | ---- |
| 移动端是独立路由 `/m`（可引入 Vant 等移动组件库），还是复用 `/admin` 做响应式优化？ | 工程 | **阻塞**（影响架构） |
| PWA 是否需要推送？若需要，iOS 受限如何取舍 | 产品+工程 | 非阻塞 |
| 数据看板速览的具体范围（哪些卡片） | 产品 | 非阻塞 |
| 移动端是否也需要「退学/毕业」状态下的操作限制（应复用后端已有校验） | 工程 | 非阻塞（后端已就绪，前端需对齐） |

## 8. 时间线建议（分阶段）

- **阶段一（P0）**：移动端优先布局 + 六大 P0 功能，先跑通「录入 + 速查」核心闭环
- **阶段二（P1）**：PWA 可安装 + 看板速览 + 待办提醒
- **阶段三（P2）**：按数据决定是否做推送/离线/家长端

## 附：技术方向提示（非本 PRD 范围，供工程参考）

- 复用现有 FastAPI，移动端建议**新增轻量只读/写入接口**（精简字段、免桌面端重量级序列化），与现有桌面端接口并存。
- 「随手记表现/谈心」本质是现有 `classlog`、`workbench` 模块的移动端入口，后端已具备 `ensure_student_operable` 等退学/毕业校验，移动端应**复用而非绕过**。
- 前端组件库若引入 Vant，需评估与 Element Plus 并存的体积与维护成本。
